## Findings

- **[fragile] extras/pcic_crosswalk/pcic_crosswalk.sh:379 with :387-393 and :458 (a consequence of round-1 fix 1).** With `DAYS=1` on a changed crosswalk, `pcic_export.sql` now commits the deletion of the model's stale `pcic.series` rows. Lines 387-393 then write `pcic.runs.csv.gz` and `pcic.fwa_crosswalk.csv.gz` on the new crosswalk. `pcic.series.csv.gz` is rewritten only at line 458, after the whole days step (hours). If that step fails (a `days_build.sh` year, `qa_days.sql`, or `pcic_export_days.sql` refusing), the job exits with the old `pcic.series.csv.gz` on disk, still listing the old crosswalk, beside the new runs files. The documented upload (`extras/README.md`: `for f in pcic.*.csv.gz`) would publish that pair. `load/pcic.sql:52` would then refuse it ("pcic.series.csv.gz lists days built on another crosswalk"), so every `load.sh` fails. This needs someone to upload after a failed run, but before fix 1 the window did not exist, because the export refused instead. Fix: also write `export_table pcic.series …` right after the other `export_table` calls (line 393). The database is consistent at that point: the stale rows are gone and the new rows are not yet written. Line 458 then rewrites it after `pcic_export_days.sql`.

- **[fragile] extras/pcic_crosswalk/pcic_crosswalk.sh:41-46 with :432 and :454.** `COMMIT` is captured, and the tree checked clean, once at start. The per-year build then re-reads `days_build.sh`, `pcic_days.py` and `sql/pcic_crosswalk06_daily.sql` from the working tree at each of 63 `xargs` invocations, hours later. Any commit, checkout or edit in that tree during the run builds later years with code the stamped commit does not hold. Every file still gets `fwapg.commit = $COMMIT`, which `pcic_export_days.sql` publishes. This is the "a wrong SHA satisfies every guard built to catch its absence" shape (code-check.md, "Written data outlives the fix"). It is the stated purpose of the guard (findings.md, "so that the column cannot name a commit the files were not built from"), and this session has already edited a running job's tree once (findings.md:103).

  Separately, `git diff --quiet HEAD -- . ../../load` ignores untracked files, so a new SQL file or script not yet `git add`ed passes the guard while the recorded commit lacks it. `data/` and `*.gz` are gitignored, so `git status --porcelain -- . ../../load` is empty in normal use and is the stricter test.

  Fix: use `[ -z "$(git status --porcelain -- . ../../load)" ]` for the start guard. Before line 454, assert `[ "$(git rev-parse HEAD)" = "$COMMIT" ]` and the same clean status, so a moved tree stops the catalogue. Alternatively, run the per-year build from copies frozen at start.

- **[fragile] extras/pcic_crosswalk/pcic_crosswalk.sh:417-429 (round-1 fix 2, one axis over).** Resume keeps any file whose `fwapg.crosswalk_md5` matches; the file's `fwapg.commit` is never compared. Take round 1's own sequence: a run fails, a fix is committed, the run resumes. If the fix was to `sql/pcic_crosswalk06_daily.sql`, `pcic_days.py` or `days_build.sh`, every kept year built by the old code is reused. The catalogue now names the old commit honestly, but nothing rebuilds those years, and neither the README nor the message says to delete them. For years in `YEARS`, `qa_days.sql` catches only a defect that moves the multi-year mean. Years outside `YEARS` (1950 by default, 32 years with `YEARS=1981/2010`) are checked only for row and sub-basin counts. Fix: also rebuild a kept file when its commit is empty, or when `git diff --quiet <file commit> "$COMMIT" -- days_build.sh pcic_days.py sql/pcic_crosswalk06_daily.sql` fails. Or state in the README that a change to those files needs `data/days/<model>_<scenario>/` removed.

- **[fragile] extras/pcic_crosswalk/pcic_crosswalk.sh:190 with :257-266.** `FETCH_ONLY=1` without `DAYS=1` keeps nothing for any batch whose climatology CSV already exists in `$DAILY`. Line 190 returns before the fetch whenever `DAYS=0`, the NetCDF check at 257 runs only for `DAYS=1`, and line 265 then prints `fetched <model> / <scenario>: N batches`. ## Round-1 fixes: checked, no defect

- Fix 1 (`pcic_export.sql` `:days` exemption and DELETE): the exemption and the DELETE use the same predicate, scoped to `(model, scenario)`. Another model's stale rows are still refused with `DAYS=1` (tested). Every caller passes `-v days` (`pcic_crosswalk.sh:379`, `pcic_test.sh:196`). The DELETE is pinned by a test (mutation above). Its one side effect is finding 1.
- Fix 2 (parquet metadata): files from the running build (commit 8d08a0e, no metadata) give `meta` = `,`, so the final run removes and rebuilds them, as `findings.md` plans. A `meta` that crashes on a damaged file also falls through to a rebuild. `fingerprint` refuses a file without metadata. `pcic_export_days.sql` refuses a file on another crosswalk (tested), so a wrong shell-level comparison at line 419 would fail loud, not publish. `CROSSWALK_MD5` (from `pcic.fwa_crosswalk`) and the export's md5 (from `fwapg.pcic_fwa_crosswalk`) agree, as the test's export of 2001-2003 shows.
- Fix 3 (climatology from `$LEAVES`): a missing CSV stops the job. `.missing` leaves have their empty CSV created by `fetch_batch`. Leaves come from the same `batch_leaves` the NetCDF check uses.

## Not findings (checked)

- `days_build.sh` under `/bin/bash` 3.2: no expansion after the EXIT trap is armed can be unbound (`$# -ge 5` guarantees at least one NetCDF for `"$@"`), so the bash 3.2 exit-0 trap path is not reachable.
- `06_daily`: the split preserves the old SQL exactly. Only `ORDER BY`, `fillfactor` and the table name passed through `set_config` were added. Four concurrent builds take only AccessShare locks on shared tables.
- `pcic_days.py rows`: `idx` is not asserted contiguous. A time axis carrying another year's step inside the year would misalign values silently. Hydromosaic's time axis is monotonic and `reduce_batch` would also break on it, so this is not reported.
- `qa_days.sql`'s 1e-9 absolute term covers ncdump's 15-digit printing of the double climatology on a subtraction of large outflows (about 1e-11 at 1e4 m³/s).
